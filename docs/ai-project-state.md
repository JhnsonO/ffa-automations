## 2026-08-10 session (cont.): GPU-access diagnosis corrected by Johnson (manual log review, run 31363966159)

**Prior session's diagnosis (glob-bug fix exposing an apt-version-mismatch root cause) is superseded.** Johnson reviewed the actual run log and branch script directly and found the extraction step itself is the fault, not a missing library:

- **Host's matching-version libs are already present pre-extraction.** Before the apt/dpkg extraction runs, `ldd libGLX_nvidia.so.580.65.06` cleanly resolves `libnvidia-glcore.so.580.65.06`, `libnvidia-glsi.so.580.65.06`, and `libnvidia-gpucomp.so.580.65.06` — all exact-version matches already bind-mounted from the Vast host. No missing-library condition exists at this point.
- **The extraction block itself introduces the mismatch.** It unconditionally downloads the latest 580-series package (`580.178.04`) from apt and overwrites `libGLX_nvidia.so.0`, `libcuda.so.1`, `libnvidia-ml.so.1`, etc. with that version — after which Vulkan starts requiring `libnvidia-gpucomp.so.580.178.04`, which doesn't exist, and fails. The script selects by driver series only, not exact host version.
- **A genuine pre-existing Vulkan failure remains underneath.** With the correct, un-overwritten `580.65.06` stack in place, `vulkaninfo` still fails at `vkCreateInstance`. Removing the bad extraction step will not by itself fix Vulkan — it returns the system to this still-unexplained failure, which needs isolated diagnosis next.
- **CUDA has a separate, distinct self-inflicted mismatch.** The script picks the CUDA toolkit version via `sort -V | tail -1` (always newest available), landing on CUDA 13.3 this run, while the `580.65.06` host driver reports CUDA 13.0 support. `cuInit` fails with `CUDA_ERROR_COMPAT_NOT_SUPPORTED_ON_DEVICE` as a direct result.
- **Unresolved, not yet root-caused:** `NVIDIA_VISIBLE_DEVICES` is set to `all` in the launch request but reads back as `void` inside the container at PID 1. Device nodes and host driver libs are mounted regardless, so this is not confirmed as causal — noted for future reference only.

**Corrected next direction:** do not pursue NVIDIA `.run`-installer extraction (previously proposed as option (b) — premature, host already has matching libs). Instead: (1) stop the extraction step from overwriting the already-correct host-matched driver libs, (2) pin CUDA toolkit selection to match the host driver's reported max-supported CUDA version instead of always taking newest, (3) re-run `vulkaninfo` diagnostics against the untouched, version-matched stack to isolate the real pre-existing Vulkan failure in isolation.

**Branch state:** `fix/oev-glx-glob-diag` (`a430de7`) still not merged to main — glob-fix itself is correct and enabled this diagnosis, but does not fix GPU access on its own.

## 2026-08-10 session (cont.): ROOT CAUSE FOUND AND CONFIRMED — wrong Vulkan ICD frontend for headless env. GPU acceleration is achievable.

**Deep ICD-loader diagnostic (`4be1e80`, run `31371523867`) found the real signal via `LD_DEBUG=libs`:** `libnvidia-glcore.so` (linked in by the GLX-frontend ICD, `libGLX_nvidia.so.0`) fails to initialize with fatal undefined-symbol errors on `__malloc_hook`/`__realloc_hook`/`__free_hook`/`__memalign_hook` (removed from glibc 2.34+) and `ErrorF` (an Xorg server symbol — this is a headless container, no Xorg). This cascades into the loader's generic `vkCreateInstance` failure. Initially suspected as a glibc-2.39/Ubuntu-24.04 incompatibility, but Johnson correctly identified a cleaner explanation from NVIDIA's own Release 580 docs: **in headless/no-X11 environments, `libEGL_nvidia.so.0` should be used as the Vulkan ICD instead of `libGLX_nvidia.so.0`** — the GLX frontend pulls in GLX/Xorg-dependent code paths (hence `ErrorF`) that don't belong in a headless container at all, independent of any glibc version question.

**Confirmed by targeted test (`0a0f816`, run `31376043680`, fully read-only — no system files mutated):** built a temp Vulkan ICD manifest with `library_path: libEGL_nvidia.so.0`, pointed the loader at ONLY that file via `VK_DRIVER_FILES`/`VK_ICD_FILENAMES`, left the real system `/etc/vulkan/icd.d/nvidia_icd.json` (which points at GLX) untouched. Result: **`vulkaninfo --summary` succeeded against the real GPU** — `deviceType = PHYSICAL_DEVICE_TYPE_DISCRETE_GPU`, `deviceName = NVIDIA GeForce RTX 4070 Ti SUPER`, `driverID = DRIVER_ID_NVIDIA_PROPRIETARY`, `driverInfo = 580.65.06`. No `llvmpipe` fallback. Root cause is fully closed: **this Vast.ai container's default Vulkan ICD manifest points at the wrong (GLX) frontend for a headless environment; the correct EGL frontend works cleanly with zero library changes of any kind.**

**Production fix (not yet implemented in the main script, next step):** every future dispatch on `fix/oev-glx-glob-diag` should set `VK_DRIVER_FILES`/`VK_ICD_FILENAMES` to a self-built EGL-pointing manifest (same approach as the read-only diagnostic, just applied ahead of the `reco calibrate`/`reco stitch` invocation) — this does not require touching the system's default `/etc/vulkan/icd.d/nvidia_icd.json` at all, just exporting the env var before running `reco-cli`. This should let `reco`'s own Vulkan-based renderer pick up the real GPU instead of `llvmpipe`, which is the actual M1-relevant payoff (faster stitch, not just a diagnostic curiosity).

**Both prior extraction/version-pin fixes remain correct and should stay in the script** (they prevent a real, separate class of bug — the blanket-overwrite problem — even though they turned out not to be this session's root cause). The CUDA-runtime-apt-install `Invalid cross-device link` issue (separate, non-fatal, CPU stitch doesn't need CUDA) is still open and out of scope.
